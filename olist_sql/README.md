# SQL-анализ маркетплейса Olist

**Статус:** в работе — пройдены схема и загрузка, базовые запросы, агрегаты, JOIN, подзапросы и CTE, оконные функции. Впереди: когорты и retention, воронки, оптимизация запросов.

**Стек:** PostgreSQL 18, psql, DBeaver. Весь SQL написан вручную.

## Задача

Olist — бразильский маркетплейс: связывает небольших продавцов с покупателями крупных площадок. Вопрос проекта: **почему покупатели почти не возвращаются и что в этом зависит от доставки, продавцов и регионов.**

## Данные

[Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) (Kaggle): ~100 тыс. заказов за 2016–2018, 9 связанных таблиц, около 1,4 млн строк. CSV в репозиторий не входят — их нужно скачать с Kaggle в папку `data/`.

| Таблица | Строк | Первичный ключ |
|---|---|---|
| `orders` | 99 441 | `order_id` |
| `customers` | 99 441 | `customer_id` |
| `order_items` | 112 650 | `(order_id, order_item_id)` |
| `order_payments` | 103 886 | `(order_id, payment_sequential)` |
| `order_reviews` | 99 224 | `(order_id, review_id)` |
| `products` | 32 951 | `product_id` |
| `sellers` | 3 095 | `seller_id` |
| `category_translation` | 71 | `product_category_name` |
| `geolocation` | 1 000 163 | — |

Решения по типам: почтовые индексы — `text` (иначе теряется ведущий ноль), деньги — `numeric(10, 2)`, хэш-идентификаторы — `uuid`.

## Качество данных: что пришлось исправить

1. **`review_id` не уникален** — первичный ключ упал при загрузке: один отзыв привязан к нескольким заказам. Настоящий ключ — составной `(order_id, review_id)`.
2. **`customer_id` — не человек.** Новый `customer_id` выдаётся на каждый заказ, человека определяет `customer_unique_id`: 99 441 против 96 096.
3. **Справочник категорий неполный.** Anti-join нашёл 2 категории без перевода; дописала через `INSERT` и вернула внешний ключ.
4. **8 доставленных заказов без даты доставки** — исключаются при расчёте сроков.
5. **Одна корзина дробится на несколько заказов.** 276 человек оформили 2–3 заказа в одну и ту же секунду — например, 3 штуки одного товара у одного продавца стали 3 заказами. Метрика «больше одного заказа» считала их вернувшимися.
6. **Край выгрузки.** Данные фактически обрываются в конце лета 2018: последние месяцы нельзя читать как падение продаж.

## Главные выводы

- **Опоздание отнимает 2 балла оценки из 5:** вовремя — 4,29, опоздал — 2,27 (~96 тыс. отзывов).
- **Опоздания определяет запас в обещанном сроке, а не расстояние.** Север: доставка 26–29 дней, но запас 19–21 день → опозданий 3–4%. Северо-Восток: доставка 20–25 дней, запас 9–10 дней → 15–21%.
- **Доставка из своего штата в 2 раза быстрее:** 7,9 против 15,0 дня. При этом в 4 штатах (AL, AP, RR, TO) нет ни одного продавца — 807 покупателей получают всё издалека.
- **Повторных покупок почти нет: настоящий repeat rate — 2,85%, а не 3,1%** (2 740 человек; 257 «вернувшихся» на деле оформили одну корзину).
- **Опоздание первого заказа снижает возврат примерно на 18%:** 2,34% против 2,87%. Эффект есть, но удержание низкое у всех — доставка его не объясняет. Оговорка: опоздания сконцентрированы в ноябре 2017 и феврале–марте 2018, у этих людей меньше времени вернуться до конца выгрузки.
- **Двойной подсчёт при JOIN искажает метрики:** прямое соединение позиций и платежей завышало выручку на 4–34%; при подсчёте средней оценки продавцов «плохих» выходило 6 вместо 2.
- **Рост выручки год к году — в 2,4 раза:** январь–август 2018 — 8,45 млн реалов против 3,47 млн за тот же период 2017. Полный 2017 против неполного 2018 показал бы лишь +22%.

## Рекомендации

1. **Пересчитать обещанный срок доставки по регионам.** Северо-Востоку обещать больше — меньше опозданий и выше оценки; Северу меньше — длинное обещание снижает конверсию.
2. **Привлекать местных продавцов на Северо-Востоке и Севере**, начиная со штатов без единого продавца: доставка из своего штата вдвое быстрее и реже опаздывает.
3. **Считать повторные покупки по моментам покупки, а не по заказам** (`COUNT(DISTINCT purchase_timestamp) > 1`), иначе метрика удержания завышена.
4. **Удержание — отдельная задача, не только про доставку:** даже при доставке вовремя возвращаются меньше 3% покупателей.

## Как воспроизвести

```bash
createdb olist
psql olist -f sql/01_create_tables.sql
cd olist_sql && psql olist -f sql/02_load_data.sql   # CSV в olist_sql/data/
```
Запросы из `03_explore.sql` выполняются по одному в psql или DBeaver.
